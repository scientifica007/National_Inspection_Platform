# Scenario Tests — Domain Fitness

هذه السيناريوهات ليست UI tests بعد. هي اختبارات صلاحية للنموذج المفاهيمي.

يجب أن يستطيع الـDomain تمثيل كل سيناريو دون hard-coded special case غير مبرر.

1. مفتش ميداني يعمل منفردًا وينشئ خطة زيارة خاصة به ثم ينفذها.
2. مفتش عضو في فريقين متزامنين بدورين مختلفين.
3. مفتش مركزي يكون عضوًا مؤقتًا في فريق يقوده مفتش مركزي آخر دون تغيير رتبته الرسمية.
4. فريق جغرافي يستمر رغم تغيير جميع أعضائه.
5. فريق موسمي يتشكل في فترة دخول تكويني ثم يغلق، ويمكن تشكيل دورة جديدة لاحقًا.
6. المفتش العام يقود فريقًا مباشرة في مهمة محددة.
7. Admin ينشر مهمة اختيارية لفئة مؤهلة؛ أحد المفتشين يختار تنفيذها وتصل المعلومة إلى مصدر المهمة.
8. مهمة اختيارية لا يأخذها أحد؛ تتحول لاحقًا إلى تكليف إلزامي لمفتش أو فريق.
9. مهمة تحدد المخرجات فقط وتترك منهج التنفيذ للفريق.
10. مهمة أخرى تحدد خطوات ومراجع ومخرجات إلزامية بدقة.
11. مفتش ينشئ مؤسسة محلية ويستعملها فورًا ثم يقترح اعتمادها.
12. مفتش ينشئ Checklist محلية؛ تعتمد لاحقًا لفريق ثم تنشر على نطاق أوسع دون فقدان منشئها وتاريخ النسخ.
13. Visit تستخدم نسخة مرجع v3؛ يصدر v4 لاحقًا ولا تتغير الزيارة التاريخية.
14. مفتش يثبت Finding؛ Admin لا يستطيع تعديل نصها، لكن يمكن إضافة Amendment موثق.
15. تقرير فريق يجمع مساهمات عدة أشخاص مع بقاء provenance لكل مساهمة.
16. تتغير علاقة بلدية بدائرة/ولاية؛ التقارير التاريخية تبقى قابلة للقراءة وفق البنية السارية في وقتها.
17. المفتش له ولاية سكن وولاية تكفل إداري/مالي وولاية عمل حالي مختلفة.
18. Dashboard الوزير ينتقل من حصيلة وطنية إلى ولاية ثم مؤسسة ثم مهمة ثم سجل مصدر.
19. Dashboard المفتش ينتقل من حصيلة شخصية إلى مهمة أو مؤسسة أو فترة أو منطقة.
20. تغيير تصميم الواجهة بالكامل لا يتطلب تعديل قواعد الـDomain أو إعادة كتابة السجلات.

## معيار النجاح

لا ينتقل المشروع إلى التنفيذ البرمجي لمجرد أن الملفات موجودة.  
ينجح M0 عندما تكون المفاهيم والعلاقات والقواعد كافية لشرح هذه السيناريوهات بصورة متماسكة ويمكن تحويلها إلى Acceptance Criteria قابلة للاختبار.
